# 台本負荷の測定

現在の上限である20行までの表示・保存・音声処理を測る。実エンジンの生成速度・音質・物理端末での総メモリーは別の検証対象とする。

## 実行方法

Node.js 24で`npm ci`と`npx playwright install --only-shell chromium`を済ませ、ほかの重い処理を止めて実行する。

```sh
npm run benchmark:script
```

本番ビルド後に専用サーバーを`127.0.0.1:3212`で起動し、1ワーカーで24ケースを実行する。通常のE2Eには含めず、制限時間の引き上げや性能値による成否判定は行わない。端末間で時間の閾値を共通にせず、同じ条件での変更前後を比較する。

動作確認だけなら、反復と表示を指定できる。

```sh
npm run benchmark:script -- --project=desktop --repeat-each=1
```

終了時に表示される`.local-artifacts/script-benchmark/<日時>/report.md`が集計、同じ場所の`report.json`が生データである。成功した各反復を別々に残し、失敗・中断があればレポートの状態と終了コードに反映する。Markdownの「回数」が実際に集計した件数である。失敗した測定を成功値で補わない。

レポートには日時・GitのHEAD/未コミット変更の有無・Node/ブラウザの版・OS/CPU/搭載メモリー・反復設定・台本と音声のサイズを保存する。ソースを編集中に実行した場合は`dirty: true`となる。生データ・トレース・ダウンロードした合成WAVはコミット対象外で、生成したレポートを整形チェックの対象からも除く。

## 条件と確認内容

| 行数 | 1行の音声長 | 元の形式                 | 元音声合計 | 期待結果                                 |
| ---- | ----------- | ------------------------ | ---------: | ---------------------------------------- |
| 10   | 10秒        | 24kHz / 16bit / モノラル |  約4.58MiB | 保存・結合・復元に成功                   |
| 20   | 10秒        | 24kHz / 16bit / モノラル |  約9.16MiB | 保存・結合・復元に成功                   |
| 20   | 30秒        | 48kHz / 16bit / モノラル | 約54.93MiB | 保存・結合・復元に成功                   |
| 20   | 40秒        | 48kHz / 16bit / モノラル | 約73.24MiB | 保存・結合を拒否し、現在の行別音声を保持 |

各条件でPC表示とモバイル表示を3回ずつ測る。モバイルはiPhone 13相当の表示・タッチ操作をChromiumで模擬し、ページのCPU処理を4倍に減速する。物理iPhone・Safariの結果ではなく、Workerにも同じ減速が効くかは確認していない。

新しいブラウザコンテキストごとに、最大300文字のセリフと同じ採用声のコピーを持つ合成台本を用意する。実際のアプリの作品保存・IndexedDB・音声結合を使い、すべてのブラウザAPI要求をモックまたは拒否する。外部AI・音声エンジンは呼び出さない。通常使用中のブラウザ保存は変更しない。

測定区間は次の7つ。

- `open`：ページ移動後に台本欄を開き、全行表示と生成可能状態を確認する。
- `edit`：最後の行の文章を一回の入力操作で置き換え、表示反映を確認する。
- `save-project`：作品保存欄を開き、実際にブラウザへ保存する。
- `generate-mocked`：順次生成の要求とUI更新を測る。API応答には指定の長さの合成PCMを使う。
- `save-audio`：実際のIndexedDBへ音声を保存し、容量超過ケースでは拒否を確認する。
- `join`：WAVの変換・結合と保存リンク表示までを測る。容量超過ケースでは拒否までを測る。
- `restore-audio`：再読み込み後に台本欄を開き、音声と最終行の編集内容の復元を確認する。

測定区間にはPlaywrightによるクリック・スクロール・状態確認の待機と、描画を反映する2フレームも含む。`open`と`restore-audio`はページ移動時間を含まない。純粋な関数の実行時間や1文字ごとの入力遅延ではない。

結合できたWAVは測定区間の外でダウンロードし、ヘッダー・形式・全体のバイト数と行間込みのフレーム数を照合する。保存・結合・復元で生成APIの要求数が増えないこと、容量超過後も行別音声が残ること、復元時に再生成しないこと、例外と画面の横はみ出しがないことも確認する。

## メモリーと長い処理の読み方

`longTasks`はページ側のPerformanceObserverが観測した50ms以上の処理で、`longestTaskMs`は区間内の最長値である。0は観測対象の長い処理がなかったことを表し、CPU処理が0だったことを表さない。Worker内の変換時間はページの長い処理として数えない。対応可否は`longTaskObservationSupported`で確認する。

`jsHeapUsedBytes`は各操作後にCDPで取得したページJSヒープの観測値である。ピーク値ではなく、Workerのヒープ・Blobの実体・音声デコーダー・GPU・ネイティブメモリーを含まない。Worker化の前後で値が小さくなっても、総メモリーの削減とは判断しない。`storage.usageBytes`と`quotaBytes`もブラウザによる概算で、実際の端末で使える空き容量の保証ではない。

結合処理は元Blobに加えて48kHzモノラルへ変換した各行のPCMと完成WAVを同時に持つ。たとえば20行×30秒では元音声だけで約54.93MiBあり、変換後PCMと出力を足すと約165MiBになる。これはデータ量の計算であり、実測したプロセスメモリーではない。ブラウザ内部のコピー・デコーダー等の使用量はさらに別に考える必要がある。

## 2026-10-23の測定結果

環境はdarwin/arm64、Apple A18 Pro・6論理CPU・メモリー8GiB、Node v24.14.1、Chromium 156.0.8078.4。変更前は07:06 JST、変更後は07:08 JSTに完了し、各24ケースが1回の実行で成功した。ソース編集中の測定で、両方のレポートのHEADは`bf5b474`、`dirty: true`である。変更前の本番ビルドにはWorkerがなく、変更後には`script-audio-worker`が含まれる。

今回のWorker後の結合区間では50ms以上のメインスレッドタスクを観測しなかった。PCの20行×30秒など、所要時間が増えた条件もある。Workerの起動・モジュール読み込みを含むため、全条件での処理時間短縮は保証しない。また、モバイル条件でWorkerにも同じCPU減速が効くかは未確認なので、上の時間差をそのまま物理端末での速度向上率にしない。目的は変換ループを画面から外し、中止時に実行そのものを終了できるようにすることにある。

20行×30秒/48kHzの、Worker後のその他の操作。時間は3回の中央値。

| ------------------------ | -----: | --------------: |
| 台本欄を開く             |  229.8 |           529.9 |

| 作品を保存               |  112.8 |           220.8 |

同条件の保存後の使用量の概算は約55.1MiB。20行×40秒/48kHzは入力約73.24MiBとなり、保存・結合ともに拒否され、元の20行の音声は保持された。再読み込み後は拒否された音声が復元されず、全条件で生成APIの追加要求はなかった。音声保存にはモバイル条件で最大64msの長い処理が残り、後続の改善候補とする。

ローカルの生データは`2026-10-22T22-06-15-738Z/report.json`（変更前）と`2026-10-22T22-08-33-551Z/report.json`（Worker後）。上記の値をこの文書へ記録し、生成物自体はコミットしない。

## 行数上限の判断

行数上限は20行を維持する。行数だけでは負荷を説明できず、同じ20行でも40秒/48kHzの場合は保存・結合の64MiB上限を超える。今回の測定では20行超の表示を検証していないため、50行・100行へ増やせる根拠にはしない。

20行超への対応を検討する際は、まず低メモリーの物理端末でプロセス全体のピークメモリーと中止後の解放を測る。長い台本の段階表示・場面ごとの分割と、音声長に基づく容量案内を比較する。実エンジンで順次生成したときの待ち時間・中止・部分失敗も測り、その結果から行数と容量の上限を改めて決める。
