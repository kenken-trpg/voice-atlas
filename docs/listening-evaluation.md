# 実機の動作・聴取評価

確認日：2026-10-22。自動テストは合成PCMとモックを使う。実機の音声生成・聴取評価は未実施。VOICEVOX・AivisSpeechの標準ポートは接続拒否だったため、エンジンを利用者が起動してから以下を実行する。

## 接続と最初の試聴

1. VOICEVOXかAivisSpeechをこのPCで起動する。
2. Voice Atlasの「はじめての試聴・接続を確認する」を開く。
3. 「未接続」ならアプリの起動と接続設定、「接続済み・利用できる候補がありません」なら話者・スタイルやモデルを確認する。VOICEVOXは現在のカタログにある話者・スタイルだけが対象。
4. 利用できる声とセリフを選び、「最初の試聴音声を生成」を押す。
5. 再生して確認し、必要に応じてWAVを保存する。試聴だけでは声の採用・ライブラリ登録は行わない。

最初の試聴にはAIのAPIキーは不要。画面の生成待ち時間は、話者照合・通信・生成・任意の版情報取得を含む体感待ち時間で、純粋なモデルの推論時間ではない。「待機を中止」はブラウザの待機を止め、エンジン側の処理を必ず中止するものではない。

## 共通文の評価音声を作る

```sh
# 接続状態と候補だけを表示。合成・ファイル保存は行わない。
npm run evaluate:voice

# VOICEVOX。導入済みでカタログにあるIDを指定する。
npm run evaluate:voice -- \
  --engine VOICEVOX --voice-id vv-ryusei \
  --output .local-artifacts/listening/ryusei-run-1 \
  --machine-note "使用機器と、ほかの重い処理の有無"

# AivisSpeech。引数なしの一覧で確認したUUIDとスタイル名を指定する。
npm run evaluate:voice -- \
  --engine AivisSpeech --speaker-uuid "話者UUID" --style "ノーマル" \
  --output .local-artifacts/listening/aivis-run-1
```

接続先は既存の`.env`と同じ。エンジン・モデルのインストールや起動は自動では行わない。出力先は新しいディレクトリーを指定する。既存ディレクトリーなら生成前に拒否し、前の音声を上書きしない。`.local-artifacts/`はGit対象外。

`shared/listening-evaluation.ts`の共通6文を一件ずつ生成する。通常会話、語り、疑問文、緊迫した短文、名前と数字、間のある長文を含む。感情を強制するエンジン固有命令は付けない。

VOICEVOXは中立の4軸から導出したVoice Atlasの調声値、AivisSpeechはアプリの製品別初期値を使う。VOICEVOXエンジンの無変更の標準値との比較を自動で行うコマンドではない。調声前後の比較は画面の比較機能で別途記録する。

## 生成記録

出力先の`manifest.json`は`voice-atlas-listening-run` v1。次の情報を持つ。

- 実行ID・日時、共通文と推薦式・カタログの版。
- OS・CPU・メモリー・機器の補足。APIキーやユーザー名は記録しない。
- 製品固有の候補・調声値。
- 各文のWAVファイル名、待ち時間、バイト数、音声SHA-256、取得できた生成時のエンジン情報。
- 実行状態と失敗した文。途中で失敗した場合も成功済み音声を残し、その後の文は生成しない。
- `listening.status: "not-reviewed"`。音声生成に成功しても、聴取済みや品質合格として扱わない。

WAVのハッシュは今回の音声の識別用。モデルファイルのハッシュではない。モデル・音声ライブラリの完全な再現条件を保証する記録ではない。待ち時間は初回と2回目以降を分け、同じ機器・モデル・文・設定で比較する。

## 人による聴取記録

`docs/templates/listening-review.example.json`をローカルの評価ディレクトリーへコピーし、各実行IDに対応する記録を作る。これは手動記録用の例で、アプリへの取り込み形式ではない。

各文で、読み違い・欠落・不自然な間・音割れ・音量差を記録する。音声の自然さ・聞き取りやすさは1〜5で評価し、1は利用困難、3は修正すれば利用可能、5はそのまま採用可能を目安とする。キャラクターへの適合は別の項目にし、理由も残す。評価できない項目はnullのままにする。

推薦を調整する場合は10〜20件のキャラクター設定を用意し、事前に調整用と確認用に分ける。推薦上位候補と比較用候補を同じセリフで聴き、可能なら名前・順位を隠して提示順を入れ替える。「採用したい声が上位3候補に含まれるか」と採用理由を記録する。少数の評価だけで一般的な適合率を主張しない。

## 制作工程の受け入れ確認

NPC3人・台本10行を一つの作品として準備し、次を実機で確認する。

1. 設定文または画像から演出案を作り、声を比較・採用する。
2. 採用声ライブラリから設定を比較し、キャスティング表へ確定する。
3. 台本を取り込み、声を割り当て、順に生成・試聴する。
4. 一人分の声を差し替えて、対象行だけ再生成し、変更前後を比較する。
5. 台本全体をWAVへ出力する。
6. 作品をブラウザに保存し、作品JSONも書き出す。
7. 別のブラウザ環境で作品JSONを復元し、配役・調声値・比較理由・台本を照合する。音声も移す場合は先にブラウザへ保存して音声付き作品アーカイブを書き出し、復元後に再生成なしで再利用できることを確認する。設定だけのJSONでは音声は再生成する。

利用者による初回操作の完了時間・迷った場所も記録する。音質、推薦の有用性、操作のわかりやすさ、自動テストの成否をそれぞれ分けて報告する。

Irodoriは[専用の技術検証](irodori-evaluation.md)でcaption・seed・参照音声の一貫性と生成負荷を確かめる。既存の`evaluate:voice`とは別のコマンドと記録形式で、画面や採用声ライブラリへの接続は実機評価後に判断する。
